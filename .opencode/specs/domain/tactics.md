# Tactical Detection

A tactical opportunity is a position where a forcing continuation produces a
meaningful tactical objective.

V1 tactical objectives are limited to the outcome categories defined in
`specs/PRODUCT.md` §8:

- winning material
- forcing mate
- obtaining a decisive advantage
- neutralizing a tactical threat

Detection occurs in two stages:

1. Candidate generation.
2. Deep verification.

A candidate is not considered a training puzzle until verification succeeds.

## Tactical motifs

Tactical-motif detection and labeling (forks, pins, skewers, discovered
attacks, deflections, zwischenzug, overloaded pieces, defensive tactics,
and similar) is **out of scope for V1**. The `tacticalMotifs` field on
the puzzle model is reserved for future use and must not be populated
or relied upon in V1.

V1 records the tactical objective and the verified solution sequence;
it does not assign a motif label to either.

## Candidate generation scope (Stage 1)

Stage 1 emits candidates for the **user's plies** of the analyzed game
only. ADR-026's "every analyzed ply" phrasing is read through the
product's user-side lens: tactics are detected against the side the
player is training (the `Game.userColor` side), not against the
opponent. Opponent context remains visible in Game Review but is never
a missed-tactic candidate or a Library row statistic.

Candidate rules (version 2, plan 013) are **position-centric**: a
candidate fires when a tactic was available on the user's turn — the
played move lost ≥ 5 win-%, or the opponent's previous ply conceded a
big swing, or the user's position was already decisive (missed mate /
forced win), or a small-loss quiet miss had a forcing best first move —
and the user did not play the engine's best move. The emitted set is
capped per game (`MAX_CANDIDATES_PER_GAME`) and ordered by swing size
so Stage-2 engine time stays bounded.

## Detection-pass state model

Each analysis identity (the run that produced a completed analysis,
scoped by `analysisId`) carries a detection-pass state:

```text
absent → queued → inProgress → completed | failed
```

- `absent` — no detection pass exists for the analysis (no summary row
  yet, or a pass has not been scheduled). The Library renders no
  missed-tactic item and neither missed-tactic filter outcome matches.
- `queued` — the analysis run completed and its summary was persisted;
  the pass is scheduled to run after the analysis loop.
- `inProgress` — the pass is running; its summary carries a live
  `scanProgress` counter (see below) that advances as Stage-2 candidates
  settle.
- `completed` — every raw candidate generated by the pass settled as
  `verified` or was discarded. The summary's `missedTacticCount` is
  written; `0` is a real zero.
- `failed` — one or more candidates were not verified after a bounded
  per-candidate engine retry (a flaky candidate is deferred so the rest
  of the scan completes). The summary's missed-tactic count stays absent
  (`null`), and the pass is retried on the next verification run — a
  retry is cheap because verified rows are reused and searched positions
  are ADR-018-cached.

The **absent-vs-zero** contract is fixed by `features/010` and
`domain/game-library.md`: a missed-tactic count is meaningful only when
a pass has `completed` for the analysis. Absent data is never rendered
or filtered as zero.

Detection results are scoped to the analysis identity they processed.
A re-analysis produces a new analysis identity; its detection state
starts absent again until its own pass completes (Stage 2 reuses the
ADR-018 position cache where possible).

## Persisted candidate shape

A verified tactical candidate is persisted game-scoped with natural key
`[analysisId + sourcePly]` so detection stays scoped to the analysis
identity that produced it:

- `analysisId` — the analysis identity the candidate was detected in.
- `sourceGameId`, `sourcePly`, `startingFen`, `userMovePlayed`.
- `bestMove`, `bestPv` (UCI), `wpLoss`.
- `verificationStatus`: `raw → verified | failed`. Only `verified` rows
  carry `tacticalObjective` and verification metadata; Feature 011
  consumes `verified` rows only.
- `tacticalObjective`, `candidateSolutionLength`,
  `verificationMetadata` (engine identity, analysis/classification/
  detection versions, depth, timestamp, WDL after best line),
  `detectionVersion`, `candidateGenerationVersion`, `createdAt`.

Candidates are derived data owned by their source game and removed with
it (ARCHITECTURE.md §7). Guard/threshold/verification-source changes bump
`DETECTION_VERSION` (currently 8; v5 dropped the ADR-025 difficulty
rejection floor, v6 lowered `winning_material` to 2 points, v7 removed the
unicity gate, and v8 relaxed the stabilisation stop and scoped the WDL veto
to terminal-prefix objectives — mechanics in ADR-026 and
`research/tactical-detection.md` §5) and candidate-rule changes bump
`CANDIDATE_GENERATION_VERSION` (currently 2 after the plan-013
position-centric rules); existing records retain theirs (ARCHITECTURE.md
§9).

## Scan progress (plan 013, W3)

The per-analysis summary carries an additive `scanProgress { done, total }`
while a pass has Stage-2 work: `total` is the Stage-1 candidate count and
`done` counts candidates that settled (verified, or rejected/failed by a
Stage-2 guard). Engine-failed candidates stay pending (`done` does not
advance and the pass ends `failed`). `done` is persisted monotonically as
candidates settle and is restored from already-verified rows when an
interrupted pass resumes. Older rows have no `scanProgress` (absent), and
the UI draws a progress bar only while the pass is live in the session.
